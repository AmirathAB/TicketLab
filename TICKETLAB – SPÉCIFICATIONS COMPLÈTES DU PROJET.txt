1. PRÉSENTATION GÉNÉRALE
--------------------------------------------------------------------------------

Nom du projet : TicketLab

Description :
TicketLab est une application web indépendante permettant aux gérants (stands,
événements, parkings, garages, lavages, etc.) de générer en série des tickets,
flyers et affiches personnalisés avec des QR codes.

Objectif principal :
Permettre à un utilisateur de :
  - Choisir un type de support (ticket / flyer / affiche).
  - Choisir un secteur (stand / événement / parking / garage / lavage).
  - Soit uploader son propre template et y intégrer des QR codes en série.
  - Soit utiliser un template prédéfini TicketLab, modifier les textes,
    et générer une série de tickets/flyers/affiches avec des QR codes différents.

TicketLab est un projet complètement à part de Ticketche, mais il reprend
sa charte graphique (couleurs, polices, style) pour rester cohérent visuellement.

--------------------------------------------------------------------------------
2. STACK TECHNIQUE
--------------------------------------------------------------------------------

FRONTEND (TicketLab/front) :
  - Framework : React 18+
  - Build tool : Vite
  - Langage : TypeScript
  - Styling : Tailwind CSS
  - Routage : React Router (ou une seule page avec état suffit)
  - Appels API : axios
  - Gestion d'état : React hooks (useState, useReducer)
  - Authentification : stockage du token dans localStorage

BACKEND (TicketLab/back) :
  - Framework : Laravel 10+ (API-only, pas de Blade)
  - Langage : PHP 8.2+
  - Base de données : MySQL ou PostgreSQL
  - Manipulation d'images : GD ou Imagick
  - Gestion des ZIP : ZipArchive (native PHP)
  - Authentification : Laravel Sanctum (simple token)

HÉBERGEMENT / DÉPLOIEMENT (recommandations) :
  - Frontend : Vercel, Netlify, ou tout serveur statique
  - Backend : tout serveur PHP (Railway, Render, VPS, etc.)
  - Storage : local ou S3-compatible pour les templates et fichiers générés

4. AUTHENTIFICATION (SIMPLE)
--------------------------------------------------------------------------------

SYSTÈME D'AUTHENTIFICATION :
----------------------------

TicketLab utilise une authentification simple via Laravel Sanctum :

  1. L'utilisateur accède à TicketLab → s'il n'est pas connecté,
     redirection vers une page de login.

  2. Page de login :
     - Champ email
     - Champ mot de passe
     - Bouton "Se connecter"

  3. Appel API : POST /api/login
     Body : { email, password }
     Réponse : { token, user }

  4. Le token est stocké dans localStorage.

  5. Toutes les requêtes API suivantes incluent le header :
     Authorization: Bearer {token}

  6. Déconnexion :
     - Appel API : POST /api/logout
     - Suppression du token localStorage
     - Redirection vers login

ENDPOINTS D'AUTHENTIFICATION :
------------------------------

  POST /api/login
    Body : { email: string, password: string }
    Réponse succès : { token: string, user: { id, name, email } }
    Réponse erreur : { message: "Identifiants invalides" }

  POST /api/logout
    Headers : Authorization: Bearer {token}
    Réponse : { message: "Déconnecté" }

  GET /api/me
    Headers : Authorization: Bearer {token}
    Réponse : { user: { id, name, email } }

PAS DE GESTION D'ORGANISATION POUR L'INSTANT :
----------------------------------------------
  - Un utilisateur = un compte simple.
  - Pas de notion d'équipe ou d'organisation dans cette V1.
  - Les templates générés ne sont pas sauvegardés (juste téléchargés).

6. OPTION A – TEMPLATE PERSONNALISÉ (UPLOAD PAR L'UTILISATEUR)
--------------------------------------------------------------------------------

6.1. Upload du template
-----------------------
L'utilisateur upload une image (PNG ou JPG) qui servira de fond pour tous
les tickets/flyers/affiches à générer.

Interface :
  - Zone de drag & drop ou bouton "Parcourir".
  - Aperçu de l'image uploadée.
  - Validation : format PNG/JPG, max 10 Mo.

6.2. Définition de la zone QR
-----------------------------
L'utilisateur doit définir où placer le QR code sur son template.

Deux sous-options possibles :

  1. Zone interactive (recommandé) :
     - L'image du template est affichée dans un container.
     - L'utilisateur dessine un rectangle pour définir la zone QR.
     - Les valeurs x, y, width, height sont calculées automatiquement.
     - Possibilité de redimensionner et déplacer le rectangle.

  2. Zone manuelle :
     - 4 champs input : x, y, width, height (en pixels).
     - Aperçu de la zone sous forme de rectangle rouge sur l'image.

Dimensions QR recommandées (prédéfinies) :
  - Petite : 150 x 150 px
  - Moyenne : 200 x 200 px
  - Grande : 250 x 250 px

Ces dimensions doivent correspondre aux QR codes générés par Ticketche.

6.3. Upload du ZIP de QR codes
------------------------------
L'utilisateur upload un fichier ZIP contenant N images de QR codes.
Chaque image est un QR code unique (ex: QR pour un ticket unique).

Contraintes :
  - Format : PNG (recommandé) ou JPG
  - Nom des fichiers : peu importe (qr1.png, ticket-001.png, etc.)
  - Nombre de QR = nombre de tickets/flyers/affiches à générer
  - Taille max du ZIP : 50 Mo

Interface :
  - Input file accept=".zip"
  - Affichage du nom du fichier et du nombre de QR détectés (optionnel).
  - Message d'erreur si le ZIP est vide ou invalide.

6.4. Génération des tickets
---------------------------
L'utilisateur clique sur "Générer les tickets".

Interface pendant la génération :
  - Spinner ou barre de progression.
  - Message : "Génération en cours... (X/30 tickets)"
  - Bouton "Annuler" (optionnel).

Côté serveur (Laravel) :

  1. Réception des fichiers :
     - background_image (template)
     - qr_zip (ZIP des QR codes)
     - qr_zone (x, y, width, height)

  2. Dézippage du fichier QR :
     - Extraction dans un dossier temporaire.
     - Récupération de la liste des fichiers images.
     - Tri des fichiers par nom (ordre alphabétique).

  3. Boucle de génération :
     Pour chaque QR code (ex: 30 fois) :
       a. Charger l'image template (background_image).
       b. Redimensionner le QR code pour qu'il corresponde à qr_zone.
       c. Insérer le QR code sur l'image à la position (x, y).
       d. Sauvegarder l'image générée (ex: ticket_001.png, ticket_002.png, …).

  4. Création du ZIP final :
     - Tous les tickets générés sont ajoutés dans un fichier ZIP.
     - Nom des fichiers dans le ZIP : ticket_001.png, ticket_002.png, etc.

  5. Téléchargement :
     - Le serveur renvoie le ZIP en téléchargement.
     - Nom du fichier : tickets_YYYY-MM-DD_HH-mm-ss.zip
     - L'utilisateur reçoit un fichier contenant N tickets, chacun avec
       un QR code différent intégré au bon endroit.

  6. Nettoyage :
     - Suppression des fichiers temporaires après téléchargement.

7. OPTION B – TEMPLATE PRÉDÉFINI TICKETLAB
--------------------------------------------------------------------------------

7.1. Galerie de templates
-------------------------
Après avoir choisi type + secteur, l'utilisateur voit une galerie de templates
prédéfinis correspondant à sa sélection.

Exemples de clés de templates :
  - ticket_stand_v1
  - ticket_lavage_v1
  - flyer_evenement_v1
  - affiche_parking_v1
  - etc.

Pour l'instant, 2 templates sont disponibles :
  - ticket_stand_v1
  - ticket_lavage_v1

Les autres seront ajoutés plus tard, mais la logique doit être générique.

Interface :
  - Grille de cartes (2 ou 3 par ligne).
  - Chaque carte affiche :
      - Aperçu du template (image)
      - Nom du template
      - Bouton "Sélectionner"
  - Template sélectionné mis en évidence.

7.2. Structure d'un template prédéfini
--------------------------------------
Chaque template est défini par :

  - Une image de fond (PNG/JPG).
  - Une zone QR prédéfinie (x, y, width, height).
  - Une liste de champs texte éditables, chacun avec :
      - key (ex: "event_name", "event_date", "location", "price")
      - label (texte affiché dans l'UI)
      - type (text / textarea)
      - position (x, y)
      - style (fontSize, fontFamily, color, align, maxWidth, etc.)

Exemple de structure JSON pour un template :

{
  "id": 1,
  "type": "ticket",
  "sector": "stand",
  "name": "Ticket Stand V1",
  "image_url": "https://...",
  "width": 1200,
  "height": 600,
  "qr_zone": {
    "x": 900,
    "y": 80,
    "width": 200,
    "height": 200
  },
  "fields": [
    {
      "key": "event_name",
      "label": "Nom de l'événement",
      "type": "text",
      "x": 80,
      "y": 80,
      "maxWidth": 600,
      "fontSize": 36,
      "fontFamily": "Inter",
      "color": "#ffffff",
      "align": "left"
    },
    {
      "key": "event_date",
      "label": "Date et heure",
      "type": "text",
      "x": 80,
      "y": 130,
      "fontSize": 20,
      "fontFamily": "Inter",
      "color": "#cbd5e1",
      "align": "left"
    }
  ]
}

7.3. Éditeur de template
------------------------
Quand l'utilisateur clique sur un template :

  - L'image du template est affichée en grand.
  - Les champs définis dans `fields` sont affichés comme des inputs
    positionnés au-dessus de l'image (absolument positionnés).
  - L'utilisateur peut modifier le texte de chaque champ.
  - La prévisualisation se met à jour en temps réel (le texte change
    directement sur l'image).

Interface :
  - Container avec l'image en fond.
  - Inputs absolutely positioned selon x, y.
  - Style des inputs :
      - Fond transparent
      - Bordure fine au focus (primary)
      - Police Inter, taille selon fontSize du template
  - Bouton "Suivant" activé quand tous les champs obligatoires sont remplis.

7.4. Upload du ZIP de QR codes
------------------------------
Comme pour l'option A, l'utilisateur upload un ZIP contenant N QR codes.
Le nombre de QR = nombre de tickets/flyers/affiches à générer.

7.5. Génération des tickets
---------------------------
L'utilisateur clique sur "Générer".

Côté serveur (Laravel) :

  1. Réception des données :
     - template_id
     - fields (objet avec les valeurs saisies par l'utilisateur)
     - qr_zip (ZIP des QR codes)

  2. Chargement du template :
     - Récupération des infos du template en BDD.
     - Chargement de l'image de fond.

  3. Dézippage du fichier QR.

  4. Boucle de génération :
     Pour chaque QR code :
       a. Charger l'image du template.
       b. Pour chaque champ dans `fields` :
          - Récupérer la valeur correspondante.
          - Dessiner le texte sur l'image à la position (x, y)
            avec le style défini (police, taille, couleur, alignement).
       c. Insérer le QR code dans la zone QR prédéfinie.
       d. Sauvegarder l'image générée (ticket_001.png, etc.).

  5. Création du ZIP final et téléchargement (comme pour l'option A).

10. ENDPOINTS API
--------------------------------------------------------------------------------

AUTHENTIFICATION :
------------------

  POST /api/login
    Body : { email: string, password: string }
    Réponse succès : { token: string, user: { id, name, email } }
    Réponse erreur 401 : { message: "Identifiants invalides" }

  POST /api/logout
    Headers : Authorization: Bearer {token}
    Réponse : { message: "Déconnecté" }

  GET /api/me
    Headers : Authorization: Bearer {token}
    Réponse : { user: { id, name, email } }

TEMPLATES :
-----------

  GET /api/templates
    Params : type (optionnel), sector (optionnel)
    Headers : Authorization: Bearer {token}
    Réponse : [
      {
        "id": 1,
        "type": "ticket",
        "sector": "stand",
        "name": "Ticket Stand V1",
        "image_url": "https://...",
        "width": 1200,
        "height": 600,
        "qr_zone": { "x": 900, "y": 80, "width": 200, "height": 200 },
        "fields": [ ... ]
      }
    ]

GÉNÉRATION :
------------

  POST /api/generate/custom
    Headers : Authorization: Bearer {token}, Content-Type: multipart/form-data
    Body :
      - background_image (file)
      - qr_zone (string JSON : {"x": ..., "y": ..., "width": ..., "height": ...})
      - fields (string JSON, optionnel)
      - qr_zip (file)
    Réponse : Fichier ZIP (application/zip)
    Nom du fichier : tickets_YYYY-MM-DD_HH-mm-ss.zip

  POST /api/generate/preset
    Headers : Authorization: Bearer {token}, Content-Type: multipart/form-data
    Body :
      - template_id (int)
      - fields (string JSON : { event_name: "...", event_date: "..." })
      - qr_zip (file)
    Réponse : Fichier ZIP (application/zip)

12. CONTRAINTES ET BONNES PRATIQUES
--------------------------------------------------------------------------------

PERFORMANCE :
  - PAS de limite de nombre de tickets (peut être 1, 30, 100, 500...).
  - La génération de 30–100 tickets ne doit pas bloquer le serveur.
  - Utiliser des dossiers temporaires et nettoyer après génération.
  - Afficher une progression côté front si possible.

SÉCURITÉ :
  - Valider les types de fichiers (images uniquement).
  - Vérifier que le ZIP contient bien des images.
  - Sanitiser les textes avant de les dessiner sur les images.
  - Authentification requise pour tous les endpoints de génération.

EXPÉRIENCE UTILISATEUR :
  - Messages d'erreur clairs (fichier invalide, ZIP vide, etc.).
  - Indicateur de chargement pendant la génération.
  - Aperçu clair du template avant génération.
  - Bouton "Télécharger" automatique après génération.

ÉVOLUTIVITÉ :
  - La structure des templates (JSON) doit être générique.
  - Le code de génération doit supporter n'importe quel template
    respectant le format, pas seulement les 2 premiers.
  - Prévoir d'ajouter plus tard :
      - Templates flyers, affiches
      - Plus de secteurs
      - Export PDF
      - Historique des générations (optionnel)

TICKETLAB – SPECIFICATIONS V2 (CHARTE EXTRAITE DU TEMPLATE FOURNI)

1. OBJECTIF
TicketLab est une application indépendante de Ticketche, avec son propre frontend React et son propre backend Laravel. Elle permet de générer en série des tickets, flyers et affiches à partir d’un template et d’un ZIP de QR codes. Le nom du produit est TicketLab.

2. PARCOURS UTILISATEUR
1) Connexion simple par email et mot de passe.
2) Choix du support : ticket, flyer ou affiche.
3) Choix de l’usage : stand, événement, parking, garage ou lavage.
4) Choix du mode :
   A. Template personnel : upload d’une image PNG/JPG, placement d’une zone QR prédéfinie ou libre, upload d’un ZIP de QR codes, génération d’un ZIP final.
   B. Template TicketLab : affichage des templates correspondant au choix, édition des champs directement sur l’image, upload d’un ZIP de QR codes, génération d’un ZIP final.

3. MODE A – TEMPLATE PERSONNEL
- L’utilisateur upload son propre design.
- Il choisit une taille QR prédéfinie compatible avec les QR Ticketche ou dessine/déplace/redimensionne la zone QR.
- Le système conserve la zone en coordonnées réelles de l’image : x, y, width, height.
- Le ZIP contient N QR images. N est exactement le nombre de fichiers générés.
- Le backend extrait le ZIP, trie les images, duplique le template N fois, place un QR différent sur chaque copie, puis crée un ZIP final.

4. MODE B – TEMPLATE PRÉDÉFINI
Templates initiaux à intégrer : ticket_stand_v1 et ticket_lavage_v1. La logique doit accueillir ensuite les tickets de stand/événement, les flyers de stand/événement et les tickets de parking/lavage/garage.
Chaque template contient : image, type, usage, dimensions, qr_zone, fields éditables. Les champs sont définis en JSON avec key, label, type, x, y, fontSize, fontFamily, color, align, maxWidth et required.
L’utilisateur voit le template, modifie les champs en direct, puis le backend dessine les textes et le QR sur chaque copie avant de renvoyer un ZIP.

5. CHARTE GRAPHIQUE EXTRAITE DE L’IMAGE FOURNIE
Important : les couleurs ci-dessous sont des couleurs dominantes extraites de l’image JPEG fournie. Elles peuvent légèrement varier à cause de la compression, des dégradés et de l’anti-aliasing. Les couleurs des futurs templates devront rester dans cette palette.

Palette principale :
- Jaune/or : #FFB400 — titres, accents, encadrés de valeur, éléments actifs.
- Sarcelle sombre : #015F69 — fond principal sombre.
- Sarcelle moyen : #037580 — fond principal/zone centrale.
- Sarcelle clair : #087D86 — variations et formes du fond.
- Vert-sarcelle : #226E61 — encadré secondaire et blocs d’information.
- Vert-sarcelle alternatif : #267060 — formes/dégradés décoratifs.
- Blanc : #FFFFFF — QR, logo, textes principaux et surfaces claires.
- Noir : #000000 — modules des QR codes.
- Texte foncé sur jaune : #156660 — texte de contraste dans les blocs jaunes.

Couleurs fonctionnelles recommandées :
- Succès : #10B981.
- Erreur : #EF4444.
- Avertissement : #FFB400.
- Bordure claire : rgba(255,255,255,0.18).
- Bordure accent : #FFB400.

Style visuel : fond sarcelle avec formes géométriques et dégradés, accent jaune vif, grands titres blancs ou jaunes, cartes aux angles arrondis, bordures fines jaunes, QR dans un conteneur blanc arrondi, contraste élevé.

6. POLICES
Le template fourni montre une police sans-serif arrondie et épaisse. Utiliser en priorité la police officielle déjà utilisée par Ticketche si elle est disponible dans le dépôt. Sinon utiliser Inter comme police applicative de fallback : Inter, system-ui, -apple-system, sans-serif.
Poids : 400 normal, 500 medium, 600 semibold, 700 bold, 800 extra-bold.
Pour les textes de tickets, utiliser une sans-serif lisible. La police choisie doit être disponible côté frontend et backend pour garantir que l’aperçu et le rendu final correspondent.

7. STACK
Frontend : React 18+, Vite, TypeScript, Tailwind CSS, React Router, Axios, React hooks ou Zustand, JSZip uniquement pour inspection optionnelle du ZIP.
Éditeur : HTML/CSS positionné ou Konva/Fabric.js. La prévisualisation doit respecter l’échelle de l’image.
Backend : Laravel 10+ ou 11+, PHP 8.2+, API-only, Sanctum pour tokens, MySQL/PostgreSQL, Imagick recommandé (GD en fallback), ZipArchive.
Repos : ticketlab-front et ticketlab-back, totalement séparés de Ticketche.

8. AUTHENTIFICATION SIMPLE
- POST /api/login : email, password → token et user.
- GET /api/me : utilisateur courant.
- POST /api/logout : révocation du token.
- Le frontend stocke le token et l’envoie en Bearer sur les routes protégées.
- Aucun système d’organisation ou d’équipe requis en V1.

9. API
GET /api/templates?type=&sector= : liste des templates.
POST /api/generate/custom : background_image, qr_zone JSON, qr_zip.
POST /api/generate/preset : template_id, fields JSON, qr_zip.
Les deux routes de génération sont protégées par authentification et répondent avec un fichier application/zip.

10. DONNÉES TEMPLATE
Table templates : id, type, sector, name, description, image_path, width, height, qr_zone_json, fields_json, is_global, timestamps.
qr_zone_json : {x, y, width, height}.
Les coordonnées sont exprimées en pixels dans la résolution originale du template.

11. VALIDATION ET GÉNÉRATION
- Accepter PNG/JPG pour les templates et images QR.
- Vérifier que le ZIP est valide et contient uniquement des images.
- Trier les QR de façon déterministe.
- Ne pas imposer de limite métier au nombre de tickets. Le système doit supporter 1, 30, 100 ou davantage ; appliquer seulement les limites techniques nécessaires du serveur et expliquer les erreurs.
- Générer ticket_001.png, ticket_002.png, etc., puis un ZIP final.
- Nettoyer tous les fichiers temporaires.
- Préserver la netteté des QR : fond blanc, dimension carrée, pas de déformation si possible.
- Afficher loading, progression ou message d’attente côté frontend.

12. ARBORESCENCE
Frontend : src/api, src/components/auth, src/components/wizard, src/components/editor, src/pages, src/hooks, src/types, src/utils, App.tsx, main.tsx.
Backend : app/Http/Controllers/AuthController.php, TicketGeneratorController.php, app/Models/Template.php, app/Services/TicketImageGenerator.php, database/migrations, database/seeders/TemplateSeeder.php, routes/api.php, resources/templates/images.
